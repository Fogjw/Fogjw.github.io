接下来对 Go 端的设计和架构进行解释。

下面是本项目的 Go 模块目录结构：

介绍顺序按包依赖关系顺序，从底层向上层介绍。

enginepb

此Package是引入了官方Protobuf库，基于.proto文件生成的代码，用于将 C++ 引擎通过 Unix socket 传递来的字节流做解码和将 Go 端对 C++ 引擎的请求做编码。由于完全由官方库生成，这里不做源码解析，如果手写可以参考 C++ 引擎端的实现方法。

engine

此Package依赖enginepb，作用是作为 IPC 的客户端，利用enginepb的编码、解码能力，与 C++ 引擎通信，发送请求接收回复。

同时考虑到 C++ 引擎侧的设计是线程与事务强绑定，即同一事务在begin到commit或abort期间，占用同一个线程，因此并发能力会比像 MySQL 那样的线程与事务解耦，事务只在需要执行某指令时交给线程执行的设计弱。为了配合 C++ 引擎侧的设计，Go 端同步使用连接池，限制连接数。Go 端的连接池大小与 C++ 引擎侧保持一致，获得最大并发。

因为引擎局限性，全局并行最多是线程池大小个事务，将 Go 端的连接池设计的更大只会导致没有拿到线程的事务饥饿，在实测中如果将 Go 端的连接池大小调的更大，会导致事务饥饿，严重时死锁。

连接池

在设计中，事务分为两种，一种是单句事务，一种是多句事务，如果用户没有用显式的begin来开启事务，则执行的每条SQL都会自动begin，执行SQL，然后commit。当用户显式使用begin时，如果连续有时间T没有操作，系统会自动RollBack事务，释放连接（时间 T 可由管理者调整）。这样是为了在当前连接数少的情况下充分利用连接数，以求更高的并发，防止有用户挂机。

  1. 预连接

预连接是在Go 端启动之后即创建连接池大小个空闲连接，与懒连接相比的好处在于预连接让首次请求连接不需要等待创建连接，提高了首次请求的效率。

实现上有一点细节值得说明：预创建是异步的，即 NewPool 立即返回，填池在后台 goroutine 中进行，每条连接独立拨号，单条失败静默跳过。这样做保留了懒连接的「引擎未启动时后端照常启动」的容错——后端起来时引擎还没就绪，预建全部失败，池子为空，行为等价于旧版懒连接（借出时才拨号，报错后引擎恢复自动可用）；引擎先启动时后台几毫秒就填满池。异步化后还要注意预建与并发借出的配额竞态：入池前要检查 total < maxConns，否则并发 acquire 已抢先新建满额时预建会把连接总数撑超上限。

  1. 事务回收

前面已经说到，当用户占着连接不操作时，超时时会自动Rollback，此时会需要回收被事务占着的连接，逻辑简单来说就是异步启动一个循环，select从计时器通道传来的计时信号和关闭计时器信号，接收到计时器信号时，就调用一个函数，扫描所有连接，如果超时就进行回收，将连接断开之后，引擎侧检测到事务连接中途断开会自动回滚。

这里的并发安全论证值得记录：回收器只处理「最近活跃时间已超过超时」的事务，而一个事务只要有过请求，它的活跃时间就会被刷新——所以被回收的事务此刻不可能有在途请求，Close 不会与帧收发发生竞态。回收后连接被关闭、事务从注册表移除，并记入 timedOut 表（保留一段时间），之后使用者再拿这个 txn_id 操作，会收到明确的「事务因空闲超时被回收」错误，而不是笼统的「无效事务 id」——两者用不同的错误类型区分，前端可以给出更准确的提示。

  1. 保活连接

连接过程中可能发生错误，比如请求异常、引擎退出等，为了保证连接池中的空闲连接都是可用的，需要进行保活，保活扫描在连接池初始化的时候进行一次，之后每经过设定的保活时间间隔（默认为30s）进行一次。保活扫描会将每个空闲连接取出来异步做一次存活探测，只有读取数据阻塞到超时才是正常可用的，如果是其他情况，比如连接本身断开了，或者读到了异常数据，都是不正常的连接，保守判定为死连接。扫描之后把正常连接放回连接池，死连接清除掉新建连接到连接池。

这里有一个值得玩味的设计：探测「活着」的判据是读超时。因为引擎空闲时不会主动发任何数据，所以对一条活连接执行读操作，结果必然是阻塞直到超时——读超时反而是「活着」的证据；反之，读到 EOF（连接被对端关闭）、读到意外数据（协议错乱），都是异常。这也解释了为什么保活探测不能用 SELECT 1 这种 SQL 探测：引擎有个已知 bug，无 FROM 的 SELECT 会挂起连接，探测把自己挂死。零副作用的读探测是最安全的。

  1. 取连接

设置一个等待上限时间，池满时最多等待该时间，超时报错，避免无限等待。然后循环尝试获取连接，每轮连接中，如果有空闲连接则获取空闲连接，如果连接池不满则创建连接，如果池满，则加入等待队列，值得注意的是，加入等待队列的是一个chan struct{}，之前的Go 学习笔记有提到空结构体可以作为信号，本身是不占内存空间的，这里则是创建一个接收空结构体的通道，加入连接池等待队列，然后阻塞在select上，如果接收到通道传来的信号就进行下一轮循环尝试获取连接，或者超时从队列移除通道，返回超时报错。这里很能体会到Go 协程和通道的协作作用，在这里表现出了类似C++ 条件变量的作用，但是更加灵活易懂。

  1. 归还连接

如果连接损坏，丢弃连接，连接池中连接总数减一，这样取连接的协程会通过判断池不满建新连接在填满池。连接正常时将空闲下来的连接加入连接池的空闲连接切片，然后判断，如果等待队列中有通道，取队头通道传入信号唤醒。

为什么损坏连接必须丢弃、不能放回池复用？因为读帧读了一半失败（长度前缀读完、body 没读完）时，这条连接上的字节流状态是未知的——放回池复用，下一个请求可能读到残留的半帧垃圾。所以请求失败（读/写错误）时给连接打上 broken 标记，归还时直接丢弃、配额减一，由 acquire 的「新建」分支补上。另外，读失败不重发：这条 SQL 可能已经被引擎执行了（响应帧在传输途中丢了），重发会产生重复副作用（非幂等），所以错误如实返回上层。唯一允许重发的是写失败且是自动事务——帧还没完整到达引擎，引擎绝不会执行，此时重建连接整帧重发一次是安全的。

其他的基本上都是一些辅助功能方法了，而前面也提到事务有单句事务和多句事务，在用户没有显式执行begin时都默认每句SQL是单句事务，单句事务的SQL执行内部会取一条连接，调用连接执行api，然后归还连接，而多句事务则在begin之后保持连接，直到用户commit或rollback或超时abort。

多句事务（显式事务）在代码里体现为三个入口：Begin 取一条连接并绑定到新分配的 txnID（全局原子自增），TxnQuery 按 txnID 取回那条连接执行语句（事务亲和），EndTxn 执行 COMMIT/ROLLBACK 后归还连接。这里最核心的约束是：事务必须始终走同一条连接，因为引擎的事务是连接级会话（C++ 侧 SQLExecutor 与连接绑定），换连接 = 换了会话 = 事务丢失。

auth

这一层用于用户认证，由于设计的是多租户，因此必须要存储用户信息以及做认证。同时因为这本身就是一个数据库项目，自然是不愿意再在现在引入其他数据库服务的，在后端直接用其他存储方式也会出现崩溃一致性问题，再去实现一次 WAL 太费力也太绕远路，因此这里采取的设计是引擎自举，Go 端会在C++ 引擎侧注册一个用户表来管理用户数据，通过C++ 引擎侧天然实现的数据库服务在存储用户信息。

具体做法是 EnsureSchema：启动时执行 SHOW TABLES 查 _users 表是否存在，不存在则 CREATE TABLE _users (id INT, username VARCHAR(32), password_hash VARCHAR(95), is_admin INT, created_at VARCHAR(32))。这个过程是懒自举的：引擎未启动时失败，首请求自动重试（失败后重置 sync.Once，下次调用再试）。这样后端启动不依赖引擎先就绪，顺序无关。

另外上层Go 端与React前端的通信是靠 HTTP 请求和响应的，如果每个用户维护一条长连接，会造成极大的开销，且连接一旦断开，用户必须重新登录，这显然不会带来良好的使用体验，因此设计为无状态的 HTTP 请求与响应，在信息中加入验证身份的 token ，后端会通过对 token 验证来确定是哪个用户发来的请求，从而能精准地对该用户账户下的数据库做相应操作。

JWT

JWT（JSON Web Token） 是一种紧凑且自包含的开放标准，用于在各方之间以 JSON 对象的形式安全地传输信息。因为其体积小、结构简单，特别适用于分布式系统的身份认证和授权场景。

JWT 由三段组成，用点号分隔：header.payload.signature。header 声明签名算法（本项目是 HS256）；payload 是携带的信息（本项目是用户身份）；signature 是用密钥对前两段算出的签名，签名是防篡改的关键——任何一方改了 payload 内容，签名就对不上，服务器验签直接拒绝。

JWT 为什么能实现无状态认证？ 因为服务器在签发 token 时用密钥算了一次签名，之后每个请求验签时重算签名做比对——签名对得上，说明这个 token 确实是我们签发的、且内容没被篡改过。验签全程只做 HMAC 计算，不查任何存储，这就是「无状态」：服务器不保存会话，身份随请求携带，验签即认证。代价是无法即时吊销：token 在过期前始终有效，要强制全员下线只能换密钥（代价是所有人都要重新登录）。

有几个点容易踩坑，单独说：

  • MINIDB_JWT_SECRET 是签名密钥，不是登录密码。它决定「谁能签发合法令牌」，泄露 = 任何人都能伪造任意用户身份。这个环境变量的语义和 MINIDB_ADMIN_USER（注册制管理员标记）很容易被混淆。
  • 缺省自动生成：New 时若密钥为空，随机生成 32 字节并打日志警告。这意味着重启后旧 token 全部失效，用户要重新登录。对演示项目可接受，甚至是个特性；Docker 部署时建议固定密钥保持登录态稳定。
  • 为什么登录之后每次请求都不用查数据库：登录那一次查 _users 表用 bcrypt 校验密码（见下节），签发 token；之后 24 小时内每个请求只做验签（纯 CPU），身份信息（uid/uname/admin）直接从 token 载荷里来。要留意 trade-off：用户改密码后，已签发的 token 在过期前依然有效（服务器不查库、不知道密码变了）。

bcrypt

bcrypt 是一种密码哈希算法，设计目标就是对抗暴力破解：内置盐（salt）——每个密码哈希前混入随机数，相同的密码得到不同的哈希，预计算彩虹表失效；并且计算代价可调（cost 因子），让每次哈希故意变慢（毫秒级），攻击者逐条爆破的速度被压制几个数量级。

与它相对的是把密码直接存明文（泄露即灾难）或可逆加密（密钥泄露即全部还原），以及不慢的普通哈希如 MD5/SHA（GPU 每秒可算几十亿次，秒破弱密码）。bcrypt 是「慢哈希 + 加盐」的行业标准选择。

注册与登录

注册的完整流程：白名单校验 → 串行化查重 → bcrypt 哈希 → INSERT → 签发 token（注册即登录）。

两个设计点值得记录：

  • 为什么注册要串行化（互斥锁）：引擎的 INSERT 语义是「同主键覆盖」而不是唯一约束报错，所以「用户名唯一」不能靠引擎保证，只能靠「查重 + 插入」两步——而两步之间如果不加锁，并发注册同名用户会双双通过查重、后写覆盖先写，用户名不唯一。串行化把并发窗口消除，代价是注册路径吞吐低（注册本来就不是高频操作，可接受）。
  • 用户名白名单同时是注入防线：^[a-zA-Z0-9_]{3,9}$ 直接消除了 SQL 拼接注入面——用户名里不可能出现引号、分号，拼进 WHERE username = '...' 永远安全。这是「既然要约束命名，就顺手把注入面关掉」的一举两得。

登录流程对称：SELECT 取哈希 → bcrypt.CompareHashAndPassword 比对 → 签发 token。这里有一个防枚举的细节：用户不存在、密码错误、用户行损坏，统一返回「用户名或密码错误」，攻击者无法通过报错差异探测某个用户名是否注册过。

tenant

这一层实现多租户，是整个 Go 端业务逻辑最重的部分。

多租户

多租户（Multi-tenancy） 指一套系统同时服务多个互不相关的用户/组织（租户），每个租户的数据彼此隔离、互不可见，但共享底层资源。典型例子是云数据库：不同客户买同一台机器上的数据库实例，各自建库建表，互不干扰。

本项目是单引擎共享的租户模型：所有用户共用同一个 C++ 引擎进程，隔离靠平台层（Go 端）实现。这带来一个根本问题：引擎是通用 SQL 引擎，它不认识「用户」——引擎眼里只有表，没有「这张表是谁的」。所以多租户语义（库归属、表归属、配额、越权校验）全部要在 Go 端落地。

实现方案对齐了 MySQL 的做法——元数据也放在系统表里：

  • 引擎只看到物理表 t1、t2、t3…（短名）；
  • 用户、库、逻辑表名的三层语义全部记录在 _databases、_catalog 两张系统表里；
  • Go 端在请求入口把用户写下的逻辑 SQL 改写成物理 SQL（users → t5），引擎无感。

这样引擎保持纯净（不认识租户），租户逻辑集中在一个包，符合低耦合。

系统表

和 _users 一样引擎自举：SHOW TABLES 查存在，无则 CREATE。_catalog 创建时还要插入一条保留行 (1, 0, '__next_seq__', '0')，physical_name 列存的是下一个可用的 seq 数字，作物理名分配器（后面建表小节细说）。

这里有一个容易忽略的坑：catalog 表第 0 列必须是引擎要求的 INT 主键（引擎规定每表第 0 列必须 INT/BIGINT 且同主键覆盖）。直觉上应该用 db_id 当主键——但同库要建多张表，db_id 相同会互相覆盖，所以必须加一个自增 id 作主键，db_id + table_name 的唯一性靠查重保证。这是引擎约束反推表结构设计的一个例子。

物理名分配（建表）

建一张表不是一条 SQL 的事，而是一个引擎事务：锁 seq 行 → 建物理表 → 写 catalog → 推进 seq → COMMIT。

关键点：

  • FOR UPDATE 行锁：并发建表时，多个事务都去读 seq 行，FOR UPDATE 让它们排队，后到者等先到者 COMMIT 后才能读——分配永远不重复。行锁串行化是引擎事务能力的直接应用，和「MySQL 自增主键分配」是同一类设计。
  • 崩溃一致性论证：引擎的 DDL 是隐式提交、不回滚的（kSchemaTxn，对齐 MySQL 语义），所以「建物理表成功、写 catalog 前崩溃」会留下孤儿物理表——由启动 reconcile 收敛（见后文）；「catalog 写了、seq 没推进」则下次分配同一个 seq，引擎报表名冲突——防御路径是乐观重试 +1（正常流程不会触发）。这里没有两阶段提交，靠的是固定顺序 + 对账兜底的最终一致，这是在对齐引擎能力的前提下能做到的最简方案。

SQL 改写

用户写的是逻辑表名，引擎只认物理表名，中间要一层改写。难点在于：SQL 里的字符串字面量不能碰。比如 INSERT INTO t VALUES ('FROM users')，字符串里的 FROM users 如果被当成关键字处理就会破坏语义。

因为改写只碰表名位置、只做子串替换，字符串里的关键字天然安全；且改写发生在校验库归属之后，用户只能改写自己库里的表名。

配套的还有错误消息反查：引擎报错（比如 table not found: t7）里是物理名，用户看不懂。MapError 用正则找消息里的 t\d+ 片段，逐个反查 catalog 映射回逻辑名，用户看到的永远是「自己的表名」。同理，SHOW TABLES 也要做租户过滤：引擎返回全部物理表，catalog 过滤出当前库的，返回逻辑名。

删表与删库

删表有个必须处理的坑：只让引擎删物理表、不清理 catalog 的话，会留下幽灵记录——表从引擎没了，但 catalog 里还记着，后果是表列表里「删了还显示」，更严重的是删库时遍历 catalog 逐个 DROP，撞上已不存在的物理表，引擎报错 → 整个删库请求变成 503。所以 dropTable 是两步：引擎 DROP TABLE t7 + DELETE FROM _catalog WHERE db_id=.. AND table_name='..'。删库 DropDatabase 同理：先遍历 DROP 所有物理表（对幽灵记录容错：DROP 失败就跳过，靠后面的 catalog DELETE 统一清理），再清 catalog 行、清库行。

配额与归属校验

云平台防滥用：每用户 3 个库、每库 10 张表（MaxDBsPerUser / MaxTablesPerDB 常量）。建库/建表前先数当前数量，超限返回明确的业务错误。

owner 校验是隔离的根基：所有租户操作（建表、查表、删库、切库）先 dbOwnedBy 确认「这个库的 owner_id == 当前用户的 uid」，否则返回「数据库不存在或无权访问」——不区分「不存在」和「无权限」，避免探测别人库名。这个校验在 Preprocess 入口统一做，逻辑表名改写也只在校验通过后进行。

reconcile

前面提到建表两步非原子会留孤儿，reconcile 就是启动时的对账收敛：

  • 引擎有、catalog 无 → 孤儿物理表（建表崩溃残留 / 引擎默认演示表）→ DROP；
  • catalog 有、引擎无 → 脏记录（删表崩溃残留）→ DELETE catalog 行。

两个容易翻车的细节：系统表永不参与清理（_users/_databases/_catalog/_schema 白名单跳过）；__next_seq__ 保留行不能删——它的 physical_name 列存的是 seq 数字（如 '7'）而不是表名，一旦被当成「引擎不存在的表」清掉，物理名分配器就废了。这是脏记录清理逻辑里必须显式跳过的特例（row[cNamex] == seqRowName 跳过）。

错误分层

Go 端到 HTTP 层的错误分三层，这个约定贯穿所有包：

  • 请求层错误（JSON 解析错、方法不对）→ HTTP 4xx；
  • 业务层（SQL 报错、表不存在、配额超限、事务失效）→ HTTP 200 + {ok:false, msg:...}——SQL 报错是正常业务结果，不是服务故障；
  • 后端故障（引擎连不上、池借出超时）→ HTTP 503。

业务错误的实现是给错误类型加一个标记接口 Biz() bool，handler 用 errors.As 断言区分：能断言到就按 200+ok:false 返回，否则 503。联调时踩过的坑：引擎返回业务错误时 Go 的 err 是 nil（错误信息在 res.Msg 里），曾有一版代码只查 err 不查 res.OK，导致 SQL 报错被当成成功、租户层静默假成功。现在所有引擎查询必须检查 res.OK。

handler

handler 是 HTTP 层，把「浏览器发来的 HTTP 请求」翻译成「引擎调用」，解析请求、调用连接池、回写 JSON。业务逻辑（SQL 改写、建表分配事务）在 tenant，协议细节（帧/编解码）在 engine，handler 把各层串起来。

/api/query 是唯一入口，完整链路：

事务分派

分派逻辑本身不复杂，核心是把「事务语义」翻译成连接池的三个入口。两个细节：

  • BEGIN 响应带 txn_id 和 idle_timeout_s：前端拿到 txn_id 供后续语句携带；拿到空闲超时秒数可以显示倒计时（事务快被回收的提醒），这是「显式告知使用者」的 API 设计。
  • 错误分层在此落地：事务失效/超时回收是业务状态错误 → 200+ok:false（同时清理 txnDB 条目）；引擎故障 → 503。

txnDB：事务内免带 db_id

连接池已经维护了 txnID → 连接 的映射，但多租户层还需要 txnID → db_id（事务内语句要知道在哪个库里改写 SQL）。handler 维护一个 txnDB map：BEGIN 成功时绑定，COMMIT/ROLLBACK 时清理。这样事务内语句可以只带 txn_id、不带 db_id，与连接池的事务亲和语义保持一致。这是「后端无状态」原则的一个有意的例外——事务是连接级会话，库上下文随会话保持是同一语义的延伸。

metrics

指标层是 admin 专属的可观测性：请求计数 + 慢查询环形缓冲 + QPS 秒窗口，全部内存态（重启清零），通过 /api/metrics 暴露（admin 才能看——单引擎共享架构下这些是平台全局统计）。

实现要点：

踩过的坑：时钟抖动会越界 panic。 QPS 桶下标 = 当前秒 - 窗口起点秒，在 WSL 环境下 NTP 校时会让时钟回拨（下标变负）或前跳（下标远超 60），直接数组越界 panic，把整个服务打崩。修复是双保险：idx < 0 归 0（回拨时归入当前桶）；idx >= 60 时起点对齐当前秒并清零（大幅前跳时历史窗口本就无意义）。这是「系统时间不是单调递增」这个反直觉事实带来的教训——之后加了回归测试锁定。

慢查询环形缓冲的展示顺序也有讲究：Snapshot 里按新→旧排列输出（从写入游标前一个开始逆序），前端直接展示最近 N 条慢 SQL。

main：装配与进程生命周期

最后看入口 main.go 怎么把这些模块装起来，以及两个容易被忽略的细节。

模块装配：读环境变量（socket 路径、监听地址、池大小、JWT 密钥、管理员用户名、慢查询阈值）→ engine.NewPool（启动即触发预创建 + 事务回收器 + 保活 goroutine）→ auth.New（懒自举 _users）→ tenant.New（懒自举系统表 + 启动 reconcile 对账）→ metrics.New → 注册路由（auth 端点、query、databases/use/tables、metrics、status）→ 静态托管前端。

静态托管：生产模式由 Go 后端直接托管 web/dist（单端口 :3000 部署）。findDist 同时探测 web/dist 和 ../web/dist（Go 进程的工作目录不一定在仓库根，两种相对位置都试）。入口页 index.html 设 Cache-Control: no-cache：js/css 带内容 hash 天然可缓存，但入口页必须每次校验——否则前端重新 build 后，浏览器还在用缓存的旧 index.html，新版本永远加载不到。这是演示项目里非常实际的「部署了但用户看不到新版」问题的解法。

优雅关闭：监听 SIGINT/SIGTERM → 先 srv.Shutdown（给在途 HTTP 请求 10 秒窗口）→ 再 pool.Close()（关闭全部连接，引擎侧检测到事务连接断开自动回滚未提交事务）→ 日志「bye」。顺序不能反：先关池会让在途请求的 SQL 突然断连。

至此，从 C++ 引擎的存储内核，到 Go 端的连接池、认证、多租户、指标与 HTTP 装配，整个系统的每一层都串起来了。回顾一下这条调用链上的「身份」与「连接」两个正交概念：连接是执行层的无主资源（8 条共享、复用、事务亲和），JWT 是应用层的身份凭证（随请求携带、验签不查库）——多租户层在请求入口拿身份做归属校验与 SQL 改写，连接池在底层保证事务语义与并发上限，各司其职。
