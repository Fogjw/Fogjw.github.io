这段时间完成了Lock Manager和Table Manager，这些都是MVCC的前置。

Lock Manager

概念解析

Lock Manager的作用是管理行锁，用于保护数据库表中的一行数据在被当前事务读写时不被其他事务读写，不过读数据其实后面是要通过MVCC的版本链读取的，所以实际的作用是防止当前事务修改一行数据时不会被其他事务同时修改。

在当前数据库的设计中，关于B+树的key-value中的key和value，key是一个表中唯一的索引，即主键id，而value是该主键对应的一行数据，比如一个账单表Order，key就是Order_id，不可重复，而value就是形如”user | item_id | price | order_time”的字符串数据，因此增删改查都是以一行数据为单位，将字符串分析为行数据，修改部分项或全部项再存入B+树，具体的解析在于后面需要做的sql模块，现在不多赘述。

那么我已经实现了B+树的Latch Crabbing，能保证多线程下对B+树的增删查改的安全性，那么为什么还需要行锁呢？

我们必须清楚的是，一个事务是由多个B+树操作组成的，而B+树的Latch Crabbing只能保证单个B+树操作的原子性，而不能保证事务的原子性。

而行锁让事务读写一个key对应的行之前都需要获取锁，这样事务在读取旧值之前上锁，在解析、计算、插入完成之后解锁，就能保证整个过程key对应的行不会被其他事务改变。

实现思路

Lock

先说Lock的具体实现，这也是Lock Manager最核心的api。首先对于Lock Manager，维护一个哈希表（可以直接使用unordered_map）存储key对应的等待队列，这个等待队列的结构如下：

我们不对表中的每个key都创建一个LockEntry，仅在有事务需要对key加锁时创建LockEntry，如果等待队列上没有事务，即销毁LockEntry。

在Lock的逻辑中，首先从哈希表中获取key的LockEntry，如果没有则创建并加入表，当然表是需要锁保护的。

然后检查等待队列中是否已经有本事务以相同LockMode（读锁或写锁）持锁（granted == true），如果有则直接返回true，因为本事务持有的锁只有事务结束才会释放，请求相同的锁不需要重复请求。

然后检查等待队列是否有本事务等待相同的LockMode，理由和前面一样，之所以要区分LockMode，是因为锁允许从读锁升级为写锁，因此如果队列中已经有不同模式的请求，还需要加上本请求。但是这里如果队列里有的话并不返回，而是继续执行，只是如果队列里没有需要加在队尾。

接着尝试获取锁，因为锁的本体就是每个请求的granted，所以需要自己写循环和条件变量，如下：

首先检查目前的条件是否允许获得锁或已经被死锁检测设置为需要回退的事务。允许获得锁的条件即在本请求的队列前面的请求都已经被授予（FIFO，防止写锁请求饥饿）且持锁与自己申请的LockMode兼容（读锁互相兼容，读写、写写、写读不兼容）。IsAborted(txn)为true的条件即能在LockManager维护的victim集合中找到本事务。

如果获得锁的条件满足或者需要回退，退出循环。否则，如果是本次请求的第一次循环，进行死锁检测。由于死锁一定是由于某个事务请求一把获得不到的锁导致的，因此只要对每个不能立刻满足拿锁条件的请求进行一次死锁检测就是覆盖所有死锁情况。死锁检测的逻辑是，每个key有一个等待队列，存放拿到了锁的事务和等锁的事务。建立有向图，对于每个key的等待队列，对于每个等锁的事务A，每个持锁的非本事务B，如果等锁的事务和持锁的事务锁不兼容，则添加一条从等锁事务到持锁事务的边（A->B）；对于每个等锁的事务A，如果队列里存在排的更靠前但在等锁的非本事务B，取最近的一个，添加一条本事务到非本事务的边（A->B）。最终的有向图如果存在环，则出现死锁，本项目假设事务号最大的事务执行的操作最少，加入victim集合，唤醒victim所在等待队列的所有事务，这些事务在循环中IsAborted(txn)为true，退出循环。

其他事务继续在在等待队列中等待唤醒，如果有事务调用UnlockAll方法，那么释放的所有key锁的队列都会被唤醒，其中的事务回重新判断尝试取锁。

在离开循环之后，首先判断是因为被要求回退还是因为获准进行授予锁。先判断是否被要求回退：

如果被要求回退，从等待队列中移除本事务全部请求，唤醒队列重新试探锁，返回false，让上层调用者明白锁获取被驳回，自行回退重试。

接下来就进行锁授予，因为已经排除了是被选为 victim 的可能，剩下的运行到这里的请求都是获准进行锁授予的，直接授予。

授予锁逻辑：选择队列中第一个本事务的请求更新granted，删除剩下的请求。因为事务内部是单线程的，所以不存在队列中同时出现多个在等锁的同一事务的请求的情况，因此不会出现先请求读key锁再请求写key锁，在读key锁的授予中删除写key锁请求的情况，只有在队列前方无本事务请求或队列前方有本事务已经授予的读锁时才会进行写锁请求。

UnlockAll

相比Lock，UnlockAll的逻辑就简单得多了。Lock已经实现了在锁请求的过程中保证了死锁检测，UnlockAll只需要保证在解锁的过程中将事务所持有的锁全部解锁(即从所有key的等待队列中找到本事务的请求进行删除)，并检查是否有删空的队列，删除删空的LockEntry。最后如果victim中有本事务，也需要从victim从删除本事务（Lock失败的事务会调用UnlockAll释放自己的锁请求）。

在初始实现中，对死锁条件判断不准确，将有向图的建边条件设置为对每个key的等待队列，对每个等锁的事务到每个持锁的非本事务建立一条边，但是这样并不准确，因为key锁归根结底是基于锁兼容和FIFO的，比如如果一个存在下面这种情况：

在这种情况下，txn=1的事务在等key2的读锁，txn=2的事务在等key1的写锁，txn=3的事务在等key1的读锁，txn=4的事务在等key2的写锁，死锁。从原逻辑分析，环应该是txn=1 -> txn=3 -> txn=1 -> txn=3，但是这是不准确的，因为txn=1和txn=3都是读锁请求，相互兼容，之所以会等锁，是出于FIFO，等待前一个未授予的锁请求。而txn=2和txn=4从FIFO考虑已经是等锁请求的第一个，但是不能获得锁是由于与持锁请求的锁类型不兼容。因此在改进的逻辑中，环应该是txn=1 -> txn=4 -> txn=3 -> txn=2 -> txn=1。

Table Manager

在本项目的初始架构中没有涉及这个模块，这是因为本项目的初始架构是单表数据库，只有一棵B+树，但是在开发B+树的过程中就已经添加了页id为0的页作为Meta Page，存储统计多表的B+树根页和头页，已经做好了多表的准备，所以上层模块也要一起适配多表。

B+树的构造函数需要传入表名，如果表名能在Meta Page找到就使用Meta Page的数据建树恢复数据，如果没有找到就会自动在Meta Page中建立新表项，但这在上层是不可接受的吗，因为上层在查询表时，查询不存在的表应该返回不存在信息，而不是建立表，因此需要上层与B+树之间需要Table Manager做中转，Table Manager的建表api会直接利用B+树构造进行建表，而查表api仅查询，不在查询失败时建表。

这个实现并不困难，这里不多赘述，但是值得一提的是删表api，在此之前我的B+树模块并没有删除树的api，因此为此我在B+树模块中增加了删除本树的api，在实现中发现了一个问题。

删除树的逻辑是，先后序遍历收集树的所有节点页id，再遍历调用缓存池的删除页的api，并更新meta页中的表项数据。但是在这个过程中，必须要保证1. 删除树的全过程应该不应该有其他线程读取到树的内容，树删除完成之后其他线程查找这个表都应该不存在，而不是锁到旧根，2. 删除树的过程中崩溃之后，能在恢复时继续完成删除，不造成页泄露。

为了实现这个逻辑，在Search、Insert、Delete的下钻取锁逻辑中，增加了对根节点的判断，如果读到根节点为无效页必须要做出相应处理，而Drop（删除树）的实现原本采用的是先锁root节点，然后从meta页中删除表项（日志+实施），再遍历树收集页（同时写删除页日志），再统一调用删除api进行删除。这样一来，虽然封锁了后续线程的进入，后续线程即使读到旧根也会在下钻逻辑中判断锁到了旧根而做正确处理，但是如果在更新表项之后崩溃，后续恢复将丢失这棵树，造成内存泄露。

因此最终选择新增了日志类型，锁根页后先遍历树收集节点页，再写Drop日志，Drop日志单条自成事务，因此不存在Undo，只有Redo，在日志中写入表名和节点页清单，这样再进行更新表项（不写日志）和删除页（不写日志），即使中间崩溃，Redo也能从Drop日志从得到需要删除的表项和页清单，不会造成页泄露。
