这次主要是完成MVCC模块。首先来介绍一下MVCC：

MVCC

MVCC(Multiversion Concurrency Control，多版本并发控制)，核心作用即让读操作和写操作互不阻塞，从而在保证事务隔离性的前提下，大幅提升数据库的并发性能。

具体来说，在并发环境下，MVCC通过为同一条数据保存多个版本快照，让读操作通过版本链快照读取，与写操作分离。这样一来，每个事务在执行时，看到的都是某一时间点的数据快照，保证事务的隔离级别。

为什么需要MVCC

在项目已经完成的工作中，已经实现了Lock Manager，通过行锁让读写、写写、写读操作互斥。那么实际上，已经能够通过行锁让事务实现隔离，那么为什么需要MVCC呢？MVCC到底是用来完成什么功能的呢？

MVCC主要对对读取数据精确性要求不高的场景，让读操作读版本快照与写操作并行，从而提高速度。比如说在购票软件上买票时，票数显示并不会在数据库中的票数变动时立即变动，只有用户显式刷新时才会获取最新值进行更新，比如电商平台的价格显示，也不会在商家调整价格后让正在浏览商品的用户感知到。这些都不是敏感的追求实时的数据，对用户视角来说，具体精确的票数并不重要，如果实时查询数据库最新值，只会拖垮数据库效率，阻塞写操作的执行。

这时候就需要MVCC进行版本隔离。我们让MVCC为每条数据维护一个版本链，系统启动时初始化时数据库数值为头节点。此后每次写数据都会新增版本链节点插入链表头，在写操作所属事务提交时，该版本链节点变为可见。快照读操作会从版本链头结点寻找第一个可见并且有效区间与自己匹配的节点的值作为读操作结果。

MVCC的机制

如上述例子，对于T1事务而言，只能读到T1事务begin时的版本快照，T2、T3的操作都在T1begin之后，所以T2、T3的操作，不管是读还是写，T1都不会感知到。而T3在T2事务commit之后begin，因此T3的版本快照包括了T2的修改。这就是事务隔离，对每个事务而言，系统状态都保持在事务begin时的状态。

快照读不要求读数据的当前精确值，以此为代价换来读写完全并行、读-读无竞争、同一事务多次读结果一致，但是写-写冲突保留，写同一数据的操作依然串行。

当然事务不能只有快照读，还要有当前读，当前读老实去获取锁读当前值。考虑如之前说过的UPDATE accounts SET balance = balance - 100 WHERE id = 1;如果内部实现是使用快照读，那么显然可能出现写操作之间相互覆盖的情况，因此写操作内部的必须使用当前读操作，保证操作原子性。数据库提供了更高并发度的快照读和获取精确值的当前读给调用者，调用者必须根据自己的业务逻辑需要选择合适的api。

本项目中MVCC的具体实现逻辑

由于上层SQL层应该通过MVCC的api操作，所以MVCC需要将底层B+树的api重新封装一层，同时需要提供事务的begin、commit等api。

begin

begin的逻辑很简单，先写一条begin日志，再初始化事务上下文，设置快照水位，也就是前面例子里说到的S，然后把本事务加入活跃事务表，活跃事务表用于其他api通过事务号获得事务上下文。

commit

首先获取事务上下文，再写commit日志，更新版本链，即更新未定型的版本区间，即介绍机制时例子中的版本链从[(∞,∞), 80] -> [(0,∞), 100]变成[(12,∞), 80] -> [(0,12), 100]，再更新已提交水位，事务的begin会设置事务的快照水位为当前的已提交水位，这样事务能看到的快照即当时已经提交的所有事务的操作之后的数据库。然后从活跃事务表中删除本事务，解除本事务所有行锁。

Abort

运行时Abort比如死锁检测时被选为victim时触发。首先获取事务上下文，然后回滚事务到事务所有操作执行之前（写操作都会将每一步操作的undo所需的数据记录到事务上下文），然后从版本链中删除本事务的未定型节点，再写Abort日志，然后从活跃日志中删除本事务。

Write

首先锁行锁（锁写锁），如果失败则说明触发了死锁，返回状态码，上层调用Abort回退。锁成功后在持写锁的情况下查询最新值（当前读），获取当前数据的版本链，如果链表头是本事务的未定型节点，直接修改节点的值（事务只有结束时会解除所有锁，因此事务持锁期间，如果有未定型节点一定是本事务的，如果有未定型节点说明本事务在此操作之前就已经修改了数据没有提交），如果链表头不是本事务的未定型节点，插入本事务的未定型节点。值得注意的是，每个值的版本链并不是在MVCC初始化时全部初始化的，因为这样会造成很大的开销。Write在发现版本链为空，而锁成功之后的当前读读到了数据，就要添加数据库的基础版本链节点，再在其之上添加本事务的未定型节点。之后再在调用B+树插入api，然后在事务上下文记录undo需要的信息。

Delete

删除操作也是写操作，因此与Write逻辑基本如出一辙，不同点在于版本链节点有一个bool字段标明值是否被删除，Write添加的节点这个字段的值是false，而Delete这个字段是true。同时因为可能在更新版本链时表被Drop从而导致刚刚插入版本链的未定型节点需要删除，因此需要判断删除是否成功，在失败时回滚刚才的版本链。然后也和Write一样，在事务上下文中记录undo需要的信息。

Read(快照读)

获取版本链，沿着版本链找到第一个可见的版本，该版本就是返回结果。如果版本链为空，可能是系统重启后还没有写操作写这条数据（写操作会检查基版本节点创建），fallback调用B+树search查询当前值，设计保证不会出现版本链不存在但数据库相关数据有未提交的改动，也就是说fallback不会查询到脏值。

ReadCurrent(当前读)

直接调用B+树api读当前值。

DropTable

删表api，原本删表应该是DDL，不属于MVCC管理的范围，但是删表会影响版本链，这里参考MySQL，选择让DDL执行时让所有事务都能感知，即如果一个事务在删表之前begin，当事务进行快照读时，读到的不是删表之前的快照，而是查询到表不存在（被删除）。

首先锁一个每个表一个的写锁（快照读和写操作都需要获得这个表的读锁，虽然写操作会修改表的数据，但是保护数据的锁有其他的，这里的读锁仅保证删表操作和其他操作互斥），然后调用Table Manager的api删除表，再将该表的相关版本链都清除掉，最后把这个表的每表一个的锁也清除掉。

GarbageCollect

GC方法用于回收资源，由main方法进行定时调用。GC会检查当前活跃事务的最小水位，将不会再被事务读到的快照删除。

首先遍历活跃事务表得到最小水位，再遍历版本链删除有效区间上界比最小水位小的版本。
