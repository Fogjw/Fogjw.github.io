2026/08/18

今天继续讲下一个模块，IPC模块，这是本项目C++引擎部分最后一个模块，在整个系统架构中，它负责与Go后端通信。因此在讲本项目的IPC实现之前，先说说IPC是什么。

IPC

IPC（Inter-Process Communication），即进程间通信。学过操作系统的都知道，进程拥有独立的虚拟内存空间，不同的进程只可见自己的虚拟内存空间，也就是进程隔离，是操作系统安全性的根基。但是从需求角度，我们难以满足于进程间完全不能通信的情况，需要进程间通信的手段，比如说不同的编程语言各有特点，但单个进程程序只能由一种语言编写、编译，要做到多语言协作，充分发挥不同编程语言的优势，必须要用到进程间通信。

所有的IPC机制本质上都在于双方通过一个都能访问的公共媒介交换字节，那么这个媒介应该由谁提供呢？内核。内核是唯一同时认识所有进程的角色，进程自己不能访问其他进程的内存，但可以通过系统调用（syscall）请求内核对公共媒介读写。

IPC通用模型：

    graph LR
A[进程 A<br/>C++ 引擎] -->|系统调用 syscall| K((内核<br/>公共媒介：管道/socket/共享内存/文件))
B[进程 B<br/>Go 后端] -->|系统调用 syscall| K
A -.普通读写.-> X[自己的私有内存]
B -.普通读写.-> Y[自己的私有内存]

IPC方式

方式 媒介 特点
管道 pipe 内核字节队列 单向/双向、简单、适合流式
消息队列 内核队列 按消息收发，有边界
共享内存 同一块物理内存 最快，但要自己加锁同步
信号 signal 内核 只能通知，不能传数据
Socket 内核网络栈端点 字节流，本机用 Unix socket，跨机用 TCP
文件 磁盘 慢但持久，WAL/数据文件就是

本项目使用的是Unix socket。Unix domain socket（UDS，Unix 域套接字）是一种IPC端点，允许同一台主机上的两个进程通过内核建立全双工、可靠的字节流或数据报通信。它的标识不是 IP + 端口，而是一个文件系统路径（如/tmp/minidb.sock或抽象命名空间名。

其实TCP也可以不出机器，比如TCP连接127.0.0.1:xxxx（本机回环）时，数据其实也不出物理网卡、也在内核里循环。但它仍然要完整走一遍 TCP/IP 协议栈：封包、解包、校验和、序列号管理、拥塞控制……只是最后发现目的地是本机，又转回内核。Unix socket则直接在内核的 socket 层交换，绕开这整条流水线——这就是它更快的原因。

跨语言通信原理

通过IPC我们能够实现将信息（如字节流）从一个进程传递给另一个进程，那么不同语言编写的进程如何识别、利用收到的信息呢？C++ 的 std::string、Go 的 string、Java 的 String 在内存里的布局完全不同，所以不能把 C++ 对象的内存直接丢给 Go 程序读。

与语言无关的只有字节流。因此必须约定一种双方认可的字节格式，即协议，双方都在发送消息前序列化（将内存中的数据结构变成双方约定的字节格式），再通过socket传递字节，接收方再按协议反序列化，将字节流还原成自己语言的类型。

本项目的IPC实现

本项目的IPC的逻辑本身是很简单的，启动，处理，关闭：

Start方法，首先初始化套接字，然后绑定到文件系统路径（TCP是绑定到IP + 端口）， 然后启动一个线程循环accept连接，将处理连接任务加入线程池任务队列，在有异常时抛出异常即可。

Stop方法，首先将运行标志置false（exchange 同时返回旧值，可判断是否重复停止），然后调用shutdown关闭监听套接字——这一步是为了唤醒阻塞在 accept() 上的线程（光置标志是不够的，accept 会一直卡住导致 join 永远等不到），随后 close 套接字、join 线程、删除 socket 文件。

HandleConnection方法，Start每连接调用一次（交给线程池执行），首先创建一个SQL执行器，然后循环从套接字读取数据，调用ProcessQuery执行，ProcessQuery内部首先是对字节流解码，再让执行器调用执行函数执行，然后编码为字节流，最后写入套接字。

相信接触过网络编程的应该都很熟悉。

因此重要的在于字节流协议的规定，本项目采用的是Protobuf wire。为什么不用JSON？首先我们是希望C++端不引入第三方库的，因为C++的ABI是编译器自己定的，没有官方的ABI，不同的编译器、不同的编译器版本都可能导致ABI不兼容，所以C++不引入外来库的价值很大。JSON也可以零依赖，但是它的payload体积是Protobuf wire的3~5倍，而且没有字段号机制，在**C++**侧手写JSON解析会比wire更复杂。

Protobuf

Protobuf，即Protocol Buffers，是Google开发的跨语言数据序列化格式，把程序内存里的数据结构变成一串字节，让别的语言/别的进程能够识别。

要使用Protobuf，首先写.proto文件，声明消息结构（字段名、类型、字段号），然后使用Protoc编译器生成代码，然后各语言就能调用序列化、反序列化方法编码、解码字节流了。不过在本项目中，C++侧不使用Protoc编译器，手写编码、解码方法来代替。

Protobuf的核心在于字段号，字节中只存字段号，不存字段名，因此双方改字段名都不影响线上兼容，同时这也使Protobuf的体积比JSON更小，且无需解析字符串，速度更快。

varint

protobuf里所有数字（字段号、长度、uint64）都用varint编码。规则：每字节 7 位数据 + 1 位”还有后续”标记，小端顺序，最高位 0 = 结束。

比如说十进制300，转为二进制为1 0010 1100，写为varint为AC 02，即1010 1100 0000 0010，反序列化时，先取第一个字节1010 1100，最高位为1，即后面还有，先取低7位010 1100在低位，取第二个字节0000 0010，最高位为0，结束，取低7为拼接到高位，即000 0010 010 1100，即1 0010 1100，即300。

编码

Protobuf每条消息的格式都是一串“tag + 内容”，tag打包字段号和类型（tag = (字段号 << 3) | wire_type），左移3位是因为wire_type有6种，但本项目只使用两种wire_type:

  • 2：长度前缀（字符串/嵌套消息）
  • 0：varint（数字）
