MiniDB：从零实现一个数据库内核——项目开发日记(1)

发表于2026-07-22|更新于2026-08-13|项目日记
|浏览量:

此文章用于记录在开发MiniDB项目中碰到的问题及解决方法，不懂的点和学习后的总结等诸多碎碎念。

项目介绍

  1. 定位：从零实现一个轻量级关系数据库，具备完整的数据库内核能力——缓冲池、索引、事务、恢复、SQL 支持。
  2. 目标：在项目开发完成时，此项目应具备能力：
  • 支持部分SQL语句（SELECT/INSERT/CREATE TABLE/DELETE）
  • 支持并发多线程读写，MVCC 快照分离
  • WAL 预写日志 + ARIES 崩溃恢复
  • 有 Web 管理面板（执行 SQL、看引擎监控）
  1. 技术栈：
  • C++17：模板、智能指针、RAII、移动语义
  • 并发编程：std::thread、std::shared_mutex、std::atomic、std::condition_variable
  • 存储引擎：B+Tree、Buffer Pool、Slotted Page、Clock-Sweep 淘汰
  • 事务与恢复：MVCC、Lock Manager、ARIES WAL
  • 网络通信：Unix Socket、Protocol Buffers
  • Web 开发：Go net/http、React + TypeScript
  • Linux 系统调用：open / pread / pwrite / fsync
  1. 项目地址：暂时私有

2026/07/22

目前已经开发完成了两个模块（src/page和src/buffer），这里做一下总结

page 模块

设计思路

考虑到持久化记录，键值存储是一定要存入磁盘的，也会需要从磁盘中读取，而我们都知道，磁盘的读写速度，尤其是随机读写速度，与内存读写相比差别过大，为了减少磁盘对性能的阻碍，必须在这方面下功夫。

考虑到操作系统与内存交互的单位是页，因此考虑设计一种数据结构存储数据page，使得每次从磁盘中读取一个page后，一个page刚好分配一个内存页，使得分配到的OS页没有外部碎片浪费，同时减少磁盘I/O次数，写操作同理。同时根据时空局限性，以页为单位读到内存，后续访问的数据也可能是页中的，增加了缓存命中率。因此本项目中设计与磁盘交互的存储单位为page，每个page占4096字节。

而对于一个page，读取到内存之后，对于其中的4096字节空间，这里做了一些设想，大致如下图

Slot存放指向对应的数据record的指针（即相对可用空间最低地址的偏移量）和数据长度。
页头存放当前页的一些信息，如页id，剩余可用空间，slot数量等

遇到的问题

在设想中，数据的长度是不一的，也正因此设计了Slot定长结构来便于定位数据，取得slot中的数据偏移和长度就能进行随机访问。因此Slot必须能通过Slot的id快速定位，有两种方式实现。

  1. SlotId存入Slot中，由于Slot定长，所以支持从可用空间最高地址向下遍历
  2. Slot从可用空间最高地址紧密排列，从占据最高地址的Slot向低地址依次id为0，1，2…，不显式存储，靠位置计算

考虑如果要删除一条数据，对于数据部分，两种方式都一样，即要么每次删除都让删除数据的高地址方向的数据移动覆盖以消除内部碎片，要么定期调用整理方法消除内部碎片。但是对于Slot部分，方式1可以将剩余空间端的Slot移动覆盖被删除的数据对应Slot，消除Slot的内部碎片，如下图

而方式2由于SlotId由位置推断，如果移动则会导致混乱，因此只回收数据部分，对应Slot仅将字段重置不指向任何数据，这会导致产生一部分的内部碎片。

经过权衡，选择方式2实现，理由如下

  1. 方式2的Slot实现仅4B（方式1需要加id字段，总计6B），虽然会产生内部碎片，但每次删除数据也只会产生4B的内部碎片，开销并不大
  2. 方式2的Slot实现使根据SlotId获取Slot的效率高得多，可以直接计算出偏移量得到Slot指针，查找时间为常数级，而方式1每次查找都需要遍历，时间开销太大

Buffer 模块

这个模块主要是用于完成缓存池，考虑数据库数据大时，频繁访问数据库必然出现内存占用高的情况，此时操作系统会进行换页，但操作系统的换页开销不可控，会换到磁盘中不确定的位置，因此缺页异常换回页时开销也不稳定，且操作系统没有脏页概念，脏页换出后需要写入数据库文件需要再换回内存，另外也难以统计命中率（以为在缓存中，但实际上被换到了磁盘上）。

缓存池限制读到内存中的页数量，只在页不被使用时换出，且换出时将脏页写回文件，能对内存中的页做精细化策略控制，缓存池自行控制留在内存中的页。

设计思路

考虑到这是一个多线程并发访问的数据结构，缓存池必须设计原子操作和互斥锁。考虑到读操作应该允许同时访问，缓存池的锁均为读写锁（在Linux上，std::shared_mutex是偏向写者的读写锁）。缓存池的换页策略设计为Clock-sweep，即当缓存页命中时，设置一个标记，需要换页时循环遍历数组，寻找符合换出条件的页，若符合但有标记，则去掉标记继续循环遍历直到找到符合条件且无标记的页。

缓存池将页封装为一个新的数据结构Frame，增加是否为脏页、Clock-sweep标记、正在使用页的线程数、每个页自己的读写锁等属性，同时用std::vector容器存放Frame，使用std::unordered_map存放页id到Frame在vector容器中的索引的映射，同时用一把shared_mutex保护这个映射表。

遇到的问题

如果需要从磁盘中加载一页到内存，或新建一个空白页，都需要从Frame数组里取出一个Frame（根据策略），若为脏页就写入磁盘，然后从pid-frame_idx映射表中删掉映射，返回这个空闲下来的frame_idx来存放内存。但是初始化未加载的Frame中的pid为0，如果直接按Frame中的pid删掉映射，可能此时有pid为0的页加载在其他的Frame，导致误删实际上在内存中的映射。因此在淘汰一页返回空闲索引方法中加入了对初始页的判断逻辑。同时学到了一个C++的细节：

Frame的Page属性中的PageHead的pid并没有显式初始化为0，但是在调用vector<Frame> frames_(pool_size_)构造时，依然会把pid初始化为0，而不会是垃圾值。这种情况叫值初始化。因为Frame作为自定义结构体没有用户自定义的构造函数时，编译器会默认生成，先将整个对象初始化为0，再调用默认构造，将显式初始化的字段进行初始化。

Btree模块

设计思路

前面我们设计了以页为单位存放数据的数据结构Page和管理页在内存与磁盘之间交互的数据结构缓存池，而B+树用于与缓存池交互，维护页节点之间的树状结构，进行查找、插入、删除操作。

为什么是B+树

关于为什么选择B+树，而不选择如数组、链表、平衡二叉树等其他数据结构：
首先我们需要明确需求，在这一模块我们要完成的是，能通过key查找到value，能将key-value插入数据结构，能通过key删除key-value，而这些操作都需要通过缓存池获取到对应的页，即在查找操作中，需要能够通过key查找到对应的存放数据的页，在页中查找数据；在插入操作中，需要通过key，找到对应的页进行插入操作，删除同理。
缓存池有大小限制，即同时存在在内存中的页有限，如果池满，要获取池中没有的页就需要与磁盘交互，而与磁盘的交互开销通常大于内存中的数次操作，因此我们需要的数据结构以减少磁盘I/O次数为目的。在最坏的情况下，可以认为每次获取页，都需要从磁盘读取（即缓存池中的页全部不命中），因此以查找时获取页的次数最少为佳。
对于只能遍历的链表，效率自然是最差的，而对于数组，假设我们维护数组有序，使用二分查找，也需要O(log N)次（N为页数）获取页并查看页的key，即最坏O(log N)次磁盘I/O，而对于平衡二叉树，也要O(log N)次（N为页数）磁盘I/O，而B+树只需要O(N)次（N为树高）磁盘I/O（节点内遍历不需要磁盘I/O），且树高比起平衡二叉树显著降低。在本项目设计中32阶B+树中，在满树的情况下，1000,000条数据的树高为4，查找最坏仅需要4次磁盘I/O，这是其他数据结构难以做到的。

B+树在本项目中的设计

在本项目中，设计为B+树的每个节点分配一页，节点内容写入页除去页头的数据区。由于需要维护32阶B+树的阶数，不定长数据可能导致一个节点中存放不了31个数据，因此舍弃了Slotted Page的数据存储形式，Page除去页头的数据区由B+树自定义的节点结构体自由分配。在目前的设计，每条数据限制为32字节时，单个节点需要的空间远远低于一页能够使用的空间，但是出于以后可能修改为单条数据更大空间，以及增加阶数不能带来明显的磁盘I/O数变化，同时带来了节点内遍历效率的降低，我没有选择增加为64阶B+树。

在B+树功能的实现上，设计两种节点，InternalNode作为内部节点，LeafNode作为叶节点，内部节点主要存储最多31个key和32个指向子节点的指针（page_id），叶节点主要存储最多31个key和value，但是在分配空间上，给内部节点多分配一个key和child的空间，叶节点多分配一个key和value的空间，用于节点满时分裂，这样就不需要先复制到临时tmp数组。区分一个页存储的是InternalNode还是LeafNode依靠页头的Flag。

遇到的一些问题

    1. 在设计底层缓存池时，暴露给上层的api考虑不周到，在原逻辑中，为了保证页在内存时正在被使用时不能被换出缓存池，因此对每个Page维护一个pin_count，在获取页时加一，使用结束减一，都需要手动调用缓存池提供的api，以及使用页的过程中需要调用对页上锁和放锁的api，在复杂的分支中，这些api经常容易产生顺序问题和遗漏问题，在编写B+树的功能函数时，不得不花费大量精力多加注意。
  • 解决方法：修改api，将检查内存中是否有需要的页，若无则从磁盘获取的FetchPage（会进行pin + 1）改为私有方法，并整合到给页上锁的LockPage中，LockPage在上锁前自行调用FetchPage进行检查，LockPage返回上锁的页指针。取消独立的UnPinPage函数，在UnlockPage中对页解锁后进行pin - 1，pin_count使用原子变量。这样一来只需要维护页的上锁和放锁即可。但是上锁和放锁操作仍然是令人厌烦的，根据RAII思想，在B+树私有区设计读写锁类，在构造函数中加锁，在析构函数中解锁，使用GetPage方法获取页指针。以写者锁为例，代码如下。这样一来，在锁对象离开作用域时即自动解锁。
    1. 节点初始化问题。由于要获得一个新的节点，必须先获得页，再向页的数据区写入节点内容。获取页指针后，直接将page->data转为节点指针使用不会触发节点的初始化，因此节点初始必须为INVALID_PAGE的字段如parent、next必须在获取新页时手动初始化，为了解决这个问题，编写了用于初始化节点的辅助函数，在每次创建新节点时手动调用。
    1. 页回收问题。当一个节点空时，应该被删除，此时这个页应该如何处理呢，由于pid的分配和数据库文件大小强相关，因此并不能随意地减小数据库文件大小。为了解决这个问题，同时为了未来对多棵B+树进行管理，固定使用pid为0的页作为MetaPage，存储不同B+树的根节点，以及空闲页pid。空闲页pid不使用数组存储，这是因为数组的大小是有限的，页大小也是有限的，因此使用头插入链表结构。MetaPage只存放链表头的pid，固定一个页被回收为空闲页时，设置数据区的前4个字节为下一个空闲页的pid。
    1. 边界问题的排查，B+树节点的插入分裂和删除合并都有复杂的边界问题，极容易出现段错误，为了排查，在关键的逻辑处设置assert断言，在函数的进入和退出打印关键信息，以便于追踪函数调用路径和错误发生原因。
